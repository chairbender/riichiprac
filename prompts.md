# Riichi Mahjong Trainer: Agent Prompts

This document contains the strict, sequential prompts to feed into DeepSeek / `opencode` to bootstrap the Riichi Mahjong Trainer. 

**Workflow Rule:** Execute these prompts one at a time. Ensure the agent successfully completes and verifies each step before feeding it the next prompt.

---

## Phase 1: Engine Foundation & WASM Pipeline

### 1. System Context Initialization
*Provide this first so the agent understands the architectural boundaries and strict constraint-satisfaction paradigm.*

**Prompt:**
> You are an expert Rust and WebAssembly developer. We are building a client-side Riichi Mahjong trainer. The architecture acts as a Constraint Satisfaction Problem (CSP) generator where the backend (Rust compiled to WASM) generates randomized game states that perfectly fit predefined constraints. 
> 
> You will strictly focus on the Rust/WASM logic and will not build any React/Vite UI. You must use the `agari` crate (https://github.com/agari-industries/agari) for all low-level Mahjong logic, including shanten, yaku validation, and ukeire calculations. All state generation must eventually rely on constructive skeletons and rejection sampling rather than brute force.

### 2. Task 1: Scaffolding the WASM Foundation
*Forces the agent to handle WebAssembly boilerplate without getting distracted by domain logic.*

**Prompt:**
> Execute Phase 1: Rust/WASM Foundation. 
> 
> 1. Initialize a new Rust library crate designed specifically to be compiled to WebAssembly via `wasm-pack`.
> 2. Configure `Cargo.toml` to set the crate type to `cdylib`.
> 3. Add the following dependencies: `wasm-bindgen`, `serde`, and `serde_json`.
> 4. Add the `agari` crate directly from its GitHub repository: `https://github.com/agari-industries/agari`.
> 5. Create a basic exposed function in `lib.rs` to verify the `wasm-bindgen` setup works.
> 
> Execute the necessary shell commands to generate the project files on disk, but do not write any Mahjong logic yet.

### 3. Task 2: JS-Based Entropy and the Generator Skeleton
*Ensures the agent uses the correct random number generation for a WASM browser sandbox.*

**Prompt:**
> Now, set up `wasm-bindgen` with JS-based entropy (`js-sys` `Math.random`) to prove we can generate and parse a single hand.
> 
> 1. Add `js-sys` and a WebAssembly-compatible RNG crate (like `rand` configured with the `wasm-bindgen` feature, or manually wrapping `js-sys::Math::random()`) to the dependencies.
> 2. Create a `ScenarioGenerator` struct or module.
> 3. Implement a function `generate_random_hand()` that uses 5-block theory to construct a basic, randomized 14-tile hand.
> 4. Feed those 14 tiles into the `agari` crate's evaluator to parse it.
> 5. Export a WASM-bound function `generate_puzzle(category: String) -> String` that returns the serialized JSON of this single parsed hand, proving the pipeline from generation to evaluation works.

### 4. Task 3: Verification and Test Harness
*Forces the agent to write WASM-specific tests to verify the pipeline before moving on.*

**Prompt:**
> Before we consider the backend foundation complete, we must prove the logic works via automated testing.
> 
> 1. Add `wasm-bindgen-test` to the development dependencies.
> 2. Write a test suite for `ScenarioGenerator` using `#[wasm_bindgen_test]`.
> 3. Write a test that generates 50 randomized hands and asserts that `agari` successfully parses every single one without panicking.
> 4. Provide me with the exact `wasm-pack test --headless` command to run these tests locally in my terminal.

### 5. Task 4: Vite/React "Hello World" Integration
*Bridges the gap to the browser to visually validate the WASM boundary and SVG rendering.*

**Prompt:**
> We need a "hello world" browser setup to visually verify the WASM pipeline. 
> 
> 1. Initialize a new Vite + React + TypeScript project in a `frontend` directory adjacent to the Rust WASM project.
> 2. Install the `riichi-mahjong-tiles` npm package.
> 3. Configure `vite.config.ts` to properly import and serve the compiled `.wasm` package generated by `wasm-pack`.
> 4. Build a single, basic React component that imports the WASM module, calls the `generate_puzzle` function on mount, and parses the returned JSON string.
> 5. Map the parsed 14-tile array to the corresponding SVG components from the `riichi-mahjong-tiles` library to render the raw hand on screen.
> 6. Provide the command to start the Vite dev server so I can view the rendered tiles in my browser.

## Phase 2: Full Game State & Mobile-First UI

### 6. Task 5: Full Game State Data Model (Rust)
*Expands the WASM payload from just a hand to a full, valid game state.*

**Prompt:**
> We are starting Phase 2. We need to expand the WASM output to represent a complete Mahjong game state before building the UI.
> 
> 1. In the Rust crate, define robust `Serialize` structs for a full table state. This must include:
>    - Global state: Round wind, hand number (e.g., East 1), Honba (repeat counters), Dora indicators, tiles remaining.
>    - Player states (array of 4): Player wind, score, hand (tiles), discards (river), melds (open calls), and Riichi status (boolean and which discard tile triggered it).
> 2. Update `generate_puzzle` to return a fully populated, mocked JSON representation of this complete state. Include dummy data for melds, discards, and at least one player in Riichi to prove the data structure works.
> 3. Verify this compiles via `wasm-pack`.

### 7. Task 6: Mobile-First Non-Skeuomorphic Layout (React)
*Sets up the stacked layout. Prevents the agent from attempting a physical square table.*

**Prompt:**
> Now switch to the React frontend. We are building a mobile-first, portrait-oriented UI. **Crucial instruction: Do NOT build a skeuomorphic, physically accurate square table layout.**
> 
> 1. Install Zustand for state management and set up a store to hold the parsed JSON game state from WASM.
> 2. Build a flexbox/grid layout that is strictly vertically stacked. 
> 3. Create 4 rows stacked on top of each other (one for each player). 
> 4. In each player's row, display only their Wind and their Discard river using the `riichi-mahjong-tiles` SVGs.
> 5. At the very bottom of the screen, pin the human player's active hand (the 14 tiles) so it is easily accessible on a mobile device.

### 8. Task 7: Advanced Player State Rendering (React)
*Iteratively adds the complex player-specific elements to the layout.*

**Prompt:**
> Let's add the remaining player-specific details to our stacked UI rows.
> 
> 1. Add Player Scores to each of the 4 player rows.
> 2. Render Melds (open calls) in the player rows alongside their discards.
> 3. Implement Riichi visuals: If a player is in Riichi, display a Riichi stick graphic in their row, and ensure the specific discard tile that triggered their Riichi is rotated 90 degrees horizontally in their discard river.

### 9. Task 8: Global Table Info (React)
*Fills in the final missing pieces of the game state.*

**Prompt:**
> Finally, let's render the global table state to complete Phase 2.
> 
> 1. Create a "Center Info" or "Header" component positioned above or amidst the player rows.
> 2. Render the current Round and Hand indicator (e.g., "East 1").
> 3. Render the Honba count.
> 4. Render the Dora indicator tiles.
> 5. Render the remaining tiles counter.
> 
> Verify the entire mocked state from the WASM payload is now accurately represented on screen.
