# Scenario history and deep linking

Task 261111-1208. Make the browser Back button return to previous scenarios, and
decide whether deep linking should ship as part of that.

## Decision

**Ship session-level Back/Forward history. Do not deep link in this change.**

Every hand the app deals becomes one browser history entry. The entry carries the
complete table plus the answer state, so Back and Forward restore the hand the
player actually saw, verdict included. The URL is left untouched.

Deep linking was evaluated and deferred: a seed in the URL cannot reproduce a hand
on this build at all (the WASM RNG is unseedable), and embedding the table in the
URL is 8–14 KB per link. Both are recorded below, along with what a future deep
link would have to look like.

## What ships

`frontend/src/scenarioHistory.ts` owns the encoding; `App.tsx` owns the React
wiring; `useGameStore.restoreSnapshot` puts a stored hand back.

- **One entry per deal.** A deal that finishes installs its hand with
  `history.pushState`, so Back steps through the hands in the order they were
  dealt. The very first hand *replaces* the launch entry instead, so Back from the
  first hand leaves the app rather than landing on a blank page.
- **What an entry holds.** The engine's own `GameState` JSON, the pool and the
  "Mortal must agree" setting the hand was drawn under, the submitted answer, the
  dual verdict, the peek flag, the armed Riichi/Kan toggles, Mortal's evaluation,
  the agreement report, and the two description fields (imported position card and
  export note). All of it lives in `history.state`, which is structured-cloned and
  has no URL length limit.
- **Answers are restored, not reset.** Going Back to an answered hand shows the
  same verdict it showed before; it does not clear the answer or re-deal. The
  entry is refreshed whenever the answer state changes (`ScenarioHistory.update`),
  so answering and then pressing Back immediately still stores the verdict for
  Forward. A refresh only lands on an entry that still records the same table, so
  a deal or import already on its way in cannot have its state written into the
  hand the player is about to leave.
- **Restores do not regenerate.** A restored hand is loaded from the stored JSON
  through the same validation as a fresh payload, and a stored evaluation is
  reused, so going back is instant and never costs another Mortal forward pass.
  The generator changing between releases cannot make an old entry invalid.
- **Failures and foreign entries.** A deal that fails leaves the current entry's
  snapshot alone (pressing Back still lands on a real hand). An entry this app did
  not write is ignored and adopted as "unclaimed", so the next deal replaces it
  instead of stacking on top of it.
- **In-flight deals are cancelled.** Navigating Back/Forward bumps the same
  `loadRequestId` guard the header and dock "Next Scenario" buttons use, so a slow
  agreement-filtered or AI deal cannot overwrite the restored hand.
- **Nothing is shareable.** The URL never changes; the history entries are a
  session-level convenience and are gone when the tab closes. Use **Export** (a
  `riichiprac.position` file) for anything that has to outlive the session or be
  sent to someone.

Both "Next Scenario" buttons already shared one handler, and that handler deals a
hand, so they push entries automatically; no button needed changing.

## Why not a seed in the URL

Compact, but it cannot work on this build without new Rust plumbing:

- `src/rng.rs` draws from `js_sys::Math::random()` on `wasm32`, and its `seed()`
  hook is `#[cfg(not(target_arch = "wasm32"))]` precisely because "the browser's
  entropy cannot be reseeded". A `?seed=` parameter would today be ignored, not
  approximate.
- Adding it means a seeded stream in the WASM build, a `generate_puzzle_seeded`
  export, and a decision about the agreement filter: that filter keeps generating
  candidates until *Mortal* agrees, so the number of RNG draws depends on the
  loaded weights. A seed pins the candidate stream, not the accepted hand, and a
  link could reproduce a hand the filter would have rejected.
- Even with a seed, the generator is rejection sampling over changing code. A
  link from an old release either fails the lesson's own constraints or quietly
  produces a different, possibly invalid, hand. Detecting that needs a fingerprint
  of the produced table compared on load — at which point the link is not durable
  anyway, only validated.

## Why not the whole state in the URL

Robust to implementation changes, but the payload is far too large for a URL.
Measured across the 32 book lessons generated by the current build:

| Measure | Size |
| --- | --- |
| `GameState` JSON, average | 5,749 characters |
| `GameState` JSON, largest (`push_or_fold`) | 10,160 characters |
| Base64/URL-encoded average | ~7.9 KB |
| Base64/URL-encoded largest | ~13.9 KB |

An AI drill is larger still: its payload also carries the full legal-action
ranking. That is 4–7× the 2 KB that stays safe through chat clients, mail
gateways, and proxies, and every history entry would carry it in the address bar.
The app already has a container for a durable, shareable position — the exported
`riichiprac.position` file, which is read back by the importer — and that is the
better tool for "send someone this hand". The URL is not.

Splitting the difference by putting the table only in `history.state` and a
scenario id in the URL would produce links that silently deal a *different* hand
under the same URL, which is worse than no link: two people opening the same URL
would see different tables.

## If deep linking is wanted later

Recommended shape, in order of preference:

1. **Seeded, validated link.** `?v=1&s=<scenario id>&seed=<u64 hex>&h=<fingerprint>`
   where `h` is a stable hash over the produced table's JSON. On load, regenerate
   the hand for `s`/`seed`, compare `h`; on match, show it and say the link
   reproduced its hand; on mismatch, deal a fresh hand from `s` and say so
   ("this link's hand is from an older version, here is a new one"). The
   fingerprint is what makes a stale seed detectable instead of silent.
   Prerequisites: seeded RNG on `wasm32` (`rng::seed` plus a seeded stream),
   `generate_puzzle_seeded(category, seed)` in `src/lib.rs`, and agreement-filtered
   links either skipped or re-recorded as "candidate N".
2. **No deep link, export/import only.** Today's answer. A hand worth keeping is a
   file, not a URL.

Whatever ships, do not mix the two models: either every deal rewrites the URL (and
the address bar becomes part of the session's state) or none does. Rewriting the
URL only for deep links makes Back/Forward behave differently depending on how the
session started.

## Verification

- `frontend/src/scenarioHistory.test.ts` covers the encoding (round trip, answer
  state, unknown fields dropped), rejection of foreign/future/malformed entries,
  first-entry replace vs push, duplicate-table suppression, refreshing an entry
  in place, and adopting a foreign entry.
- Manual/browser check (Chrome): first hand recorded by replacing the launch
  entry; header and dock "Next Scenario" each push exactly one entry; answering
  stores the answer and verdict in the entry; Back restores the previous table and
  its verdict; Back again reaches the unanswered first hand with its tiles
  enabled; Forward walks both hands again with the verdict intact; the URL never
  changes. Importing a position pushes its own entry (and Back returns to the
  dealt hand before it), and editing the export note refreshes the current entry
  in place.
